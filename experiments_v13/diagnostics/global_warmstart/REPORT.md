# 单次在线时点重排压缩：开发诊断

本诊断在原 E2/E3 各五次 **开发** 输入上，固定 R4 训练前 20,000 点；该时刻仅用已学得的当前 R4 系数对 500 个 RFF 坐标做带符号升序排序，截断 SVD 到 R2 或 R3，继承真实次级 FIR 输出历史。压缩分支从第 20,001 点一直在线更新到 400,000 点，不读取分段边界，也不在后续分段重置或重训 R4。持续 R4 仅作为配对评价参考。对照包括恒等坐标和固定随机坐标，均使用同一切换时刻、SVD、初始物理历史和步长。

E2/E3 的十次 `signed_sort_R2` 开发运行共 40 个段末窗：相对持续 R4 的 ANR 差为 **−0.793 至 +0.434 dB**，40/40 个段落在 +0.5 dB 容差内；十次运行的段平均差为 **−0.080 dB**。E2 的四段跨运行平均差为 `−0.344/−0.178/+0.007/−0.166 dB`；E3 为 `−0.269/−0.028/+0.255/+0.086 dB`。在同一五次开发输入上，当前归档 full500 RFF-MCC 相对固定 R4 的全段平均 ANR 优势为约 **2.899 dB**，其理论乘法成本也低于本压缩控制器；因此本诊断最多支持相对固定 Kronecker R4 的候选改进，**不支持优于所有 RFF 控制器**。

第零次运行的无排序 R2 与随机排序 R2 在 E2/E3 所有四段均比 R4 差约 1.9–2.9 dB；更完整的分段时点控制见 `../causal_permute/REPORT.md`。这排除了“只要先训练 R4 再做 SVD 截断，就自然得到相同结果”的简单解释，提示坐标排列改变了可压缩性和后续优化轨迹。它不是正式的归因估计，也不能从五次开发数据推断总体概率。

`../sort_rank_bound.py` 独立重放同一切换前缀：原坐标下当前 R4 系数矩阵的最佳 R2 相对 Frobenius 误差为 **0.450–0.641**；带符号排序后为 **0.033–0.091**。排序矩阵可用逐行线性函数给出一个秩至多二的条件性误差界，但此数据上的离散曲率界很宽（相对误差上界 >1），因此不作为实际降噪保证。真正的物理 ANR 改善仍须由独立实验验证。

每运行 R4 驻留 20,000 点、R2 驻留 380,000 点的主体账本为 `(20000×19132+380000×15822)/400000≈0.8357` 倍固定 R4。再按旧 v12 对库 SVD 的**约定**一次收费一百万乘法，加一次系数构造和因子缩放后，平均比约 **0.836**。这个约定不是已核实的实际分解计数；排序比较、置换访存、候选训练/验证、拒绝提案和平滑切换未包含在内。因此这个成本数只是直接切换的乐观界，**不能宣称已满足完整 10% 节省门槛**。

另用五次开发固定前沿所偏好的**同一步长** E2 `μ=0.1`、E3 `μ=0.05`，把 R4 和单次压缩分支一起重新运行。直接切换 R2 的四段质量门槛在 E2 **4/5**、E3 **4/5** 个完整运行通过；两例均为 run3 失败，最坏段差分别为 **+0.539、+0.640 dB**。40 段的总平均差 `+0.033 dB`。这取代默认步长下的 10/10 作为更公平的开发参考，也说明直接切换尚非合格的最终算法。另一个独立原型在 20k 提案后进行 2k 候选训练及 2k 因果验证，开发集上改善了 run3；该原型的完整账本和结构门控须单独核查，不能将本目录的乐观成本套到它身上。

最重要的未解问题是：20,000 点固定切换没有在线接受判据；目前没有一个在切换前依据过去物理残差判断压缩是否安全、在变化后需要时再增长的控制器。独立审计、完整成本的候选门控、固定 R1–R8 公平步长选择、新流选择及确认、MATLAB 复核仍须完成，才可写入论文主贡献。本目录没有读取 `select` 或 `confirm` 数据，也没有修改原 v10–v12 方法。

复现：

```powershell

```

无排序与固定随机排序的第零次对照需要不加 `--methods` 重跑 `--runs 0`。每次逐段结果在 `E2_run00.json` 等 JSON 文件中，代码核查包括排序下完整权重输出不变、物理 FIR 历史继承、SVD 重构和完整在线续训。此处的 `run.py` 为开发诊断，不是最终算法或正式验证运行器。
